# Mutations

While queries handle data fetching, mutations handle data modification. Use `use_mutation` to create, update, and delete data with automatic state tracking.

## use_mutation

`use_mutation` creates a mutation hook that tracks the lifecycle of an asynchronous write operation.

### Signature

```rust
pub fn use_mutation<TData, TError, TVariables>(
    cx: &mut ViewContext<impl 'static>,
    key: impl Into<QueryKey>,
    mutator: impl Fn(TVariables, QuerySignal) -> impl Future<Output = Result<TData, TError>> + 'static,
    options: MutationOptions,
) -> MutationResource<TData, TError, TVariables>
```

### MutationResource

The returned type provides reactive access to mutation state:

| Field        | Type                 | Description                                  |
| ------------ | -------------------- | -------------------------------------------- |
| `data`       | `Option<TData>`      | Result of the last successful mutation       |
| `error`      | `Option<TError>`     | Latest error                                 |
| `status`     | `MutationStatus`     | `Idle`, `Pending`, `Success`, or `Error`     |
| `is_pending` | `bool`               | Whether the mutation is in progress          |
| `variables`  | `Option<TVariables>` | Variables used for the current/last mutation |

### Basic Example

```rust
fn add_todo_form(cx: &mut ViewContext<App>) {
    let mutation = use_mutation(
        cx,
        QueryKey::from("add-todo"),
        |title: String, signal| async move {
            let response = http_client
                .post("/api/todos")
                .json(&NewTodo { title })
                .send()
                .await?;
            Ok::<_, AppError>(response.json().await?)
        },
        MutationOptions::default(),
    );

    cx.render(|_| {
        div()
            .child(
                input()
                    .on_change(|event, cx| {
                        // Store input value
                    })
            )
            .child(
                button()
                    .disabled(mutation.is_pending())
                    .on_click(|_event, cx| {
                        mutation.mutate("Buy groceries".to_string());
                    })
                    .child(if mutation.is_pending() {
                        "Saving..."
                    } else {
                        "Add Todo"
                    })
            )
    });
}
```

## mutate()

The imperative `mutate` function triggers a mutation outside of a hook context. This is useful for fire-and-forget writes.

### Signature

```rust
pub async fn mutate<TData, TError, TVariables>(
    client: &QueryClient,
    key: impl Into<QueryKey>,
    variables: TVariables,
) -> Result<TData, TError>
```

### Usage

```rust
// Fire a mutation from outside a component
async fn delete_todo(client: &QueryClient, todo_id: u64) {
    let result = mutate(
        client,
        QueryKey::from(("delete-todo", todo_id)),
        todo_id,
    ).await;

    match result {
        Ok(_) => info!("Todo deleted"),
        Err(e) => warn!("Delete failed: {}", e),
    }
}
```

## mutate_with_callbacks()

`mutate_with_callbacks` adds lifecycle callbacks to an imperative mutation. This enables side effects like cache invalidation and optimistic updates.

### Signature

```rust
pub async fn mutate_with_callbacks<TData, TError, TVariables>(
    client: &QueryClient,
    key: impl Into<QueryKey>,
    variables: TVariables,
    callbacks: MutationCallbacks<TData, TError, TVariables>,
) -> Result<TData, TError>
```

### MutationCallbacks

```rust
pub struct MutationCallbacks<TData, TError, TVariables> {
    pub on_success: Option<Box<dyn Fn(&TData)>>,
    pub on_error: Option<Box<dyn Fn(&TError)>>,
    pub on_settled: Option<Box<dyn Fn()>>,
    pub on_mutate: Option<Box<dyn Fn(&TVariables)>>,
}
```

### Usage with Cache Invalidation

```rust
async fn update_todo(client: &QueryClient, todo: Todo) {
    let result = mutate_with_callbacks(
        client,
        QueryKey::from(("update-todo", todo.id)),
        todo.clone(),
        MutationCallbacks {
            on_success: Some(Box::new(|updated| {
                info!("Updated todo: {}", updated.id);
            })),
            on_error: Some(Box::new(|e| {
                warn!("Update failed: {}", e);
            })),
            on_settled: Some(Box::new(|| {
                // Invalidate the todo list to trigger a refetch
                client.invalidate_queries(&QueryKeyFilter::prefix("todos"));
            })),
            on_mutate: Some(Box::new(|variables| {
                info!("Mutating todo: {}", variables.id);
            })),
        },
    ).await;
}
```

## use_mutation_state

`use_mutation_state` provides read-only access to a mutation's state without subscribing to the mutation itself. This is useful for showing global loading indicators.

### Signature

```rust
pub fn use_mutation_state<TData, TError>(
    cx: &mut ViewContext<impl 'static>,
    key: impl Into<QueryKey>,
) -> MutationState<TData, TError>
```

### Usage

```rust
fn global_progress_bar(cx: &mut ViewContext<App>) {
    let state = use_mutation_state::<(), AppError>(
        cx,
        QueryKey::from("batch-upload"),
    );

    if state.is_pending() {
        cx.render(|_| div().child("Upload in progress..."));
    }
}
```

<Callout type="tip">
  Always call `invalidate_queries` in `on_settled` callbacks to keep your query data fresh after
  mutations. This ensures the UI reflects the latest server state.
</Callout>

<Callout type="warning">
  Mutations do not automatically retry on failure. If you need retry logic, implement it in your
  mutator function or use `on_error` callbacks to queue a retry.
</Callout>
