# Why gpui-query?

If you've built anything non-trivial with GPUI, you've felt the pain. You spawn an async task with `cx.spawn()`, track loading state with a model field, handle errors with a match arm, and try to keep your component's render logic in sync with the async lifecycle. Then you need caching, deduplication, and retry logic — and suddenly half your component is async state management boilerplate.

**gpui-query exists to make that go away.**

## The Problem

GPUI is a powerful framework for building high-performance UIs in Rust. But when it comes to async state management, you're on your own. A typical pattern looks like this:

```rust
// Manual async state management — the old way
struct MyComponent {
    users: Option<Vec<User>>,
    loading: bool,
    error: Option<QueryError>,
}

impl Render for MyComponent {
    fn render(&mut self, cx: &mut ViewContext<Self>) -> impl IntoElement {
        cx.spawn(|this, mut cx| async move {
            this.update(&mut cx, |this, cx| {
                this.loading = true;
                cx.notify();
            })?;

            match fetch_users().await {
                Ok(users) => this.update(&mut cx, |this, cx| {
                    this.users = Some(users);
                    this.loading = false;
                    cx.notify();
                })?,
                Err(e) => this.update(&mut cx, |this, cx| {
                    this.error = Some(e);
                    this.loading = false;
                    cx.notify();
                })?,
            }
            Ok(())
        });

        // ... render logic
    }
}
```

This works, but it doesn't scale. Add caching, retry logic, request deduplication, and stale-while-revalidate behavior, and you're writing the same infrastructure code in every component.

## The Solution: TanStack Query Patterns for GPUI

TanStack Query revolutionized async state management in the JavaScript ecosystem. Its core insight was simple: **async state is fundamentally different from synchronous state**. Loading indicators, error boundaries, caching, background refetching, and deduplication are concerns that deserve first-class abstractions.

gpui-query brings these same patterns to Rust and GPUI. Here's the equivalent of the manual code above:

```rust
// With gpui-query — declarative and automatic
let query = use_query(cx, "users", || async {
    fetch_users().await
});

// query.data: Option<Vec<User>>
// query.status: QueryStatus (Idle | Pending | Success | Error)
// query.is_fetching: bool
```

Three lines replace twenty. Caching, retry, deduplication, and lifecycle management come for free.

## What Makes gpui-query Different?

gpui-query isn't a port of TanStack Query — it's an adaptation that respects Rust's strengths:

**Type-safe state machine:** `QueryStatus` is a Rust enum (`Idle | Pending | Success | Error`), not a collection of boolean flags. The compiler ensures you handle every case.

**Cooperative cancellation:** Built on `Arc<AtomicBool>`, gpui-query uses cooperative cancellation that integrates cleanly with GPUI's render loop. No `AbortController` translation — this is idiomatic Rust.

**Three-layer architecture:** The library is structured in three independent layers:

- **Core:** Pure data types and cache policies — framework-agnostic
- **Client:** `QueryClient` manages the global registry, garbage collection, and query lifecycle
- **Hook:** GPUI-specific hooks (`use_query`, `use_mutation`, `use_infinite_query`) that bind queries to component lifecycles

This separation means the Core layer is testable in isolation and could theoretically support other Rust UI frameworks.

**Zero-cost abstractions:** Query state is tracked at the type level. No runtime reflection, no dynamic dispatch on the hot path. The hook layer compiles down to the same GPUI primitives you'd use manually.

## The Feature Set

gpui-query covers the full async state lifecycle:

- **Queries** — Declarative data fetching with `use_query`
- **Mutations** — First-class mutation support with success/error callbacks
- **Infinite Queries** — Bidirectional pagination with `use_infinite_query`
- **Smart Caching** — TTL, Stale-While-Revalidate, LatestWins, IgnoreWhileLoading
- **Automatic Retry** — Configurable retry with exponential backoff
- **Cooperative Cancellation** — Signal-checked operations for clean teardown
- **Query Observers** — Direct observation of query state changes
- **Persistence** — Serialize and restore query cache across sessions
- **DevTools** — Inspect cache state via dehydrate/hydrate and diagnostics

## When Should You Use It?

gpui-query shines when your GPUI application has:

- Multiple components fetching the same data
- Complex async workflows with retry requirements
- Pagination or infinite scroll patterns
- Cache invalidation and background refresh needs
- Persistence requirements across app restarts

For a single one-off fetch in a simple component, `cx.spawn()` is fine. But as your async state grows in complexity, gpui-query scales with it — without the boilerplate.
