GPUI's render loop is synchronous, but almost everything a real app renders arrives asynchronously: language server responses, file listings, HTTP APIs, collaborator presence. So every view that touches async data grows the same plumbing. An in-flight flag. A cache with some expiry rule. A retry loop. A guard so a late response doesn't clobber state after the user has moved on.

I wrote that plumbing three times in one codebase before accepting it should be a crate.

## Borrowed ideas, Rust bones

`gpui-query` adapts the model [TanStack Query](https://tanstack.com/query) settled on for the web: you declare what data a component needs, and the library owns fetching, caching, deduplication, and cancellation. The ideas transfer well. The implementation is Rust through and through: cancellation is an `Arc<AtomicBool>` instead of an `AbortController`, cache policies are enum variants you can match on, and anything that can be checked at compile time is.

## Three layers, one crate

The crate splits into layers so you can adopt only what you need:

- `core` is a Serde-only state machine: `QueryResource`, `CachePolicy`, `RetryPolicy`, `QuerySignal`. It has no GPUI dependency and is testable in isolation.
- `client` is the GPUI `QueryClient` registry, with type-partitioned buckets for resource lifecycle, garbage collection, and persistence.
- `hook` is what your components actually touch: `use_query`, `use_mutation`, and friends.

## A query in five lines

```rust
use gpui_query::hook::use_query;
use gpui_query::{CachePolicy, QueryKey, RequestPolicy};

let (users, _subscription) = use_query(
    QueryKey::from(["users"]),
    CachePolicy::Ttl { ttl_ms: 60_000 },
    RequestPolicy::LatestWins,
    || async {
        let resp = reqwest::get("/api/users").await?;
        let users: Vec<User> = resp.json().await?;
        Ok(users)
    },
    cx,
);
```

`use_query` returns a `(data, status)` tuple, which is the Rust way to hand back two things you'll immediately destructure. The status enum carries the full lifecycle, so there's no `loading` boolean to keep in sync and no `useEffect` glue.

## What the library owns so you don't

Caching goes through `CachePolicy`, with three variants: `NoCache`, `Ttl`, and `StaleWhileRevalidate`. Failed fetches retry with fixed delays or capped exponential backoff. When a component unmounts mid-request, cooperative cancellation through `QuerySignal` means the abandoned work can stop early instead of leaking. If you want the cache to survive restarts, the `QueryPersister` trait lets you serialize it to whatever storage you have. And for paginated data there are infinite queries with fetching in both directions.

## Who this is for

If you're building anything nontrivial on GPUI and you've caught yourself re-implementing a cache, a refetch timer, or a cancellation token, this crate exists for you. Start with `use_query` and the default policies, and reach into `core` when you need custom behavior. The [getting started guide](/docs/getting-started/installation) covers setup, and if something feels off, [open an issue](https://github.com/freeoxide/gpui-query/issues).
